# 技术栈选型

## 1. 核心决策 (Key Decisions)

### 1.1 结论

纸箱自动配纸工具 V1.0 推荐采用：

**云端 Web 应用 + PWA + PostgreSQL 数据库 + 对象存储 + 服务端 AI Provider**

一句话说明：用户通过网址使用，电脑端负责高效录入和维护数据，手机端负责查看方案和导出分享；核心数据保存在云端数据库，报告文件保存在对象存储，AI 只负责生成选型理由，不参与核心计算。

### 1.2 推荐组合

| 层级 | 推荐选择 | 选择理由 |
|------|----------|----------|
| 产品形态 | 云端 Web 应用 + PWA | 满足随时随地访问，不绑定某一台电脑，也不要求用户安装软件 |
| 前端框架 | Next.js + React + TypeScript | 一个项目可同时承载页面、服务端逻辑和接口，适合首版快速落地 |
| UI 组件 | Ant Design | 表单、表格、筛选、弹窗、导入导出等后台型能力成熟 |
| 后端方式 | Next.js Server Actions / API Routes | 首版不拆独立后端项目，减少开发、部署和维护成本 |
| 主数据库 | PostgreSQL | 适合长期保存原纸、纸厂、公式参数、历史方案等结构化数据 |
| 数据访问 | Drizzle ORM | 与 TypeScript 配合紧密，类型清晰，迁移成本较低 |
| 文件存储 | OSS / COS / S3 类对象存储 | 保存 PDF、Excel、JSON 备份文件，不依赖应用服务器本地磁盘 |
| Excel/CSV | ExcelJS + PapaParse | 支持 Excel 模板、导入导出和 CSV 解析 |
| PDF 导出 | 服务端 HTML 模板 + Playwright/Chromium | 报告排版稳定，导出效果不依赖用户电脑或手机环境 |
| AI 能力 | 服务端 AI Provider + 缓存 + 模板降级 | AI 失败时不阻断方案生成，保护密钥并控制调用成本 |
| 登录安全 | 首版简单登录，后续再扩展角色权限 | PRD 首版不做复杂权限，但云端系统必须保护原纸价格和公式数据 |
| 部署方式 | 国内云优先，原型可用 Vercel/Supabase | 国内纸箱厂访问稳定性优先；原型阶段可选择更省事的平台 |

### 1.3 明确不推荐

| 不推荐项 | 原因 |
|----------|------|
| 首版做 Windows 桌面软件 | 不满足随时随地访问，后续同步和协作成本高 |
| 首版做小程序 | 复杂表格、Excel 导入、PDF 报告、数据维护体验不如 Web |
| 首版做微服务 | 当前 V1.0 是单次配纸工具，微服务会过早增加复杂度 |
| 把钉钉当主数据库 | 配纸计算需要复杂查询、公式版本、历史快照和性能保障，钉钉更适合作入口和通知 |
| 使用低代码承载核心计算 | 面积、强度、成本、设备限制和搜索策略需要可测试、可追溯的业务逻辑 |

## 2. 前端 (Frontend)

### 2.1 框架

推荐：**Next.js + React + TypeScript**

原因：

- 主流程是典型业务系统：输入参数、生成方案、调整方案、导出报告。
- 页面和服务端逻辑可放在同一个项目里，首版交付链路更短。
- TypeScript 可减少公式字段、原纸字段、方案字段在传递过程中的低级错误。
- 后续做 PWA、手机查看、钉钉工作台入口时，Web 形态更自然。

### 2.2 样式方案

推荐：**Ant Design + 少量业务定制样式**

适用原因：

- 配纸工具以表单、表格、筛选、状态标记、导入导出为主，不需要营销型页面。
- Ant Design 的表格、表单、弹窗、提示、标签、上传组件成熟，适合工艺人员和销售高频使用。
- 首版应优先清晰、稳、好录入，不追求复杂视觉效果。

界面风格建议：

- 桌面端优先，兼顾手机查看。
- 使用紧凑、清晰、可扫描的信息密度。
- 方案对比页重点突出：成本、耐破、边压、空箱抗压、是否达标、是否可生产。
- 状态标记必须清楚区分：达标、未达标、不可生产、数据不足、公式/参数异常。

### 2.3 状态管理

推荐：

- 页面局部状态：React 内置状态能力。
- 服务端数据获取与缓存：TanStack Query。
- 全局配置状态：尽量少用，必要时使用轻量状态管理。

原因：

- V1.0 主流程不复杂，避免一开始引入重型全局状态。
- 方案生成、历史方案、原纸维护都属于服务端数据，用服务端查询缓存更合适。

## 3. 后端 (Backend)

### 3.1 运行时/语言

推荐：**Node.js + TypeScript**

原因：

- 与前端共用 TypeScript 类型，减少字段口径不一致。
- 面积、强度、成本、设备限制、推荐策略都适合写成可测试的纯业务逻辑。
- Excel、CSV、PDF、AI 调用都有成熟生态支持。

### 3.2 Web 框架

推荐：**Next.js Server Actions / API Routes**

原因：

- 首版不用维护两个项目，减少部署复杂度。
- 适合当前 PRD 的单体业务：数据维护、配纸计算、导入导出、AI 理由生成。
- 后续如果用户量、接口复杂度或团队规模上升，再拆独立后端也不迟。

### 3.3 API 协议

推荐：**首版使用内部服务端动作和少量 REST 风格接口**

适用范围：

- 页面提交输入参数，服务端生成配纸方案。
- 原纸、纸厂、基础参数维护。
- Excel/CSV 导入。
- PDF/Excel/JSON 导出。
- AI 选型理由生成。

边界说明：

- 首版不需要 GraphQL。
- 首版不对外开放公共 API。
- 计算结果不可由前端手工篡改，必须以服务端重新计算为准。

### 3.4 核心业务逻辑组织

推荐把核心业务划分为以下领域：

| 领域 | 说明 |
|------|------|
| 面积计算 | 三层、五层、七层普箱面积公式和设备限制 |
| 强度计算 | 耐破、边压、空箱抗压 |
| 成本计算 | 原纸纸价、瓦楞系数、利用率、加工费用、税金、含税成本 |
| 推荐策略 | 经济型、安全型、均衡型 |
| 参数版本 | 公式、设备参数、瓦楞系数、厚度等版本追溯 |
| 导入导出 | 原纸 Excel/CSV、报告 PDF、参数 JSON、历史 Excel |
| AI 理由 | 根据计算结果生成解释，失败时模板降级 |

### 3.5 公式策略

推荐：**V1.0 内置公司默认公式，并把公式参数版本化；后续再做完整公式编辑器。**

原因：

- PRD 明确 V1.0 使用公司默认面积、强度、成本公式。
- 公式涉及中间变量、条件、设备限制和层数差异，直接让管理员自由编辑容易出错。
- 首版更重要的是把公司口径算准、可追溯、可测试。

V1.0 可维护内容建议：

- 设备尺寸参数。
- 瓦楞系数。
- 纸板厚度。
- 层数费用系数。
- 原纸利用率分段。
- 均衡型成本/安全权重。
- AI 每日调用量上限。

## 4. 数据存储 (Database)

### 4.1 主数据库

推荐：**PostgreSQL**

原因：

- 适合保存结构化业务数据：纸厂、箱板纸、瓦纸、基础参数、历史方案。
- 支持可靠的数据约束、索引、事务和 JSON 数据。
- 后续扩展角色权限、报表、多公司使用时仍有成长空间。

首版核心数据范围：

| 数据 | 说明 |
|------|------|
| 纸厂信息 | 纸厂名称、联系人、供应类型等 |
| 箱板纸信息 | 纸厂、牌号、等级、克重、纸价、耐破指数、环压指数等 |
| 瓦纸信息 | 纸厂、牌号、等级、克重、适用瓦型、纸价、耐破指数、环压指数等 |
| 基础参数 | 设备限制、瓦楞系数、纸板厚度、费用系数、利用率分段 |
| 历史方案 | 输入参数、价格快照、参数版本、方案结果、导出记录 |
| AI 缓存 | 相同输入和方案下复用选型理由，控制成本 |

### 4.2 缓存

首版推荐：**数据库缓存为主，不单独引入 Redis。**

原因：

- PRD 中历史方案只要求最近 50 条，整体数据规模不大。
- 单次方案生成目标为 5 秒内，首版可先通过分层过滤和数据库索引解决。
- Redis 可作为后续扩展项，用于高频方案、AI 调用结果或批量计算缓存。

### 4.3 文件存储

推荐：**对象存储**

保存内容：

- 完整配纸报告 PDF。
- 精简方案表 PDF。
- 原纸数据 Excel。
- 公式/参数 JSON。
- 历史方案 Excel。
- 导入模板和导入失败报告。

原因：

- 文件不应长期放在应用服务器本地。
- 后续迁移、备份、归档和钉钉分享更方便。

## 5. 基础设施 & 工具 (Infra & Tools)

### 5.1 部署

推荐路径：

| 阶段 | 推荐方式 | 说明 |
|------|----------|------|
| 原型验证 | Vercel + Supabase 或单台国内云服务器 | 快速让少数人试用 |
| 正式使用 | 国内云服务器/应用服务 + PostgreSQL 云数据库 + OSS/COS | 国内访问稳定、数据可控 |
| 后续扩展 | 独立后端服务、Redis、队列、更多权限能力 | 等业务规模真的上来再加 |

正式版本建议：

- 必须启用 HTTPS。
- 必须有登录保护。
- 数据库要有自动备份。
- 导出的文件要有访问权限控制。
- 原纸、公式参数、历史方案支持手动导出备份。

### 5.2 包管理

推荐：

| 类型 | 工具 |
|------|------|
| 前端/全栈包管理 | pnpm |
| 代码质量 | ESLint + Prettier |
| 单元测试 | Vitest |
| 端到端测试 | Playwright |
| 数据迁移 | Drizzle Kit |

原因：

- pnpm 安装速度快、依赖管理清晰。
- 公式计算、成本计算、强度计算必须有自动化测试。
- 主流程涉及导入、生成、调整、导出，适合用端到端测试保护。

### 5.3 AI 接入

推荐：**服务端统一封装 AI Provider**

要求：

- AI 只生成选型理由，不参与面积、强度、成本等核心计算。
- AI 超时、失败、达到每日上限时，必须使用模板理由。
- 不允许 AI 编造没有数据支持的结论。
- AI 输出必须基于输入参数、方案配置、计算结果和方案定位。

### 5.4 钉钉定位

推荐：**钉钉作为入口、登录、通知和文件归档，不作为主数据库。**

适合放在钉钉里的能力：

- 从钉钉工作台打开工具。
- 使用钉钉身份登录。
- 方案生成完成或导出完成后发消息提醒。
- 把最终 PDF 或 Excel 报告分享/归档到钉钉。

不建议放在钉钉里的核心数据：

- 原纸主数据。
- 公式参数。
- 历史方案。
- AI 缓存。
- 计算中间结果。

## 6. 风险与应对

| 风险 | 说明 | 应对建议 |
|------|------|----------|
| 云端安全风险 | 原纸价格、公式参数、历史方案属于核心资产 | 首版必须做登录、HTTPS、数据库备份和导出备份 |
| 国内访问稳定性 | 海外部署平台在国内访问可能不稳定 | 正式使用优先国内云，原型阶段再考虑海外平台 |
| 公式口径变化 | 面积、强度、成本公式后续可能继续调整 | 公式参数版本化，历史方案保存参数快照 |
| PDF 中文排版 | 纸箱报告字段多，表格容易变形 | 服务端生成 PDF，并用真实长表格做验收 |
| AI 不稳定 | AI 接口可能超时、失败或成本不可控 | 做缓存、限额、超时和模板降级 |
| 搜索组合过多 | 原纸组合可能数量很大 | 按层数、瓦型、强度、成本分层过滤，不盲目全量计算 |
| 首版过度设计 | 复杂权限、多租户、微服务会拖慢首版 | V1.0 坚持单体应用和简单登录 |

## 7. 后续升级路线

| 触发条件 | 升级方向 |
|----------|----------|
| 多人同时使用频繁 | 增加工艺、销售、管理员角色权限 |
| 多家公司使用 | 增加租户隔离，升级为 SaaS |
| 手机端使用频繁 | 优化移动端查看、分享、扫码访问 |
| 现场网络不稳定 | 增加离线草稿或桌面离线增强版 |
| 数据量明显增大 | 增加 Redis、队列、预计算候选组合 |
| 报告样式变多 | 增加报告模板管理 |
| 供应商价格变化频繁 | 增加价格导入接口或定时同步 |

## 8. 参考依据

- [Next.js 官方文档](https://nextjs.org/docs)：Next.js 是用于构建全栈 Web 应用的 React 框架，适合将页面和服务端能力放在同一项目中。
- [PostgreSQL 官方文档](https://www.postgresql.org/docs/current/)：PostgreSQL 支持事务、索引、约束和 JSON 等能力，适合结构化业务数据长期保存。
- [Playwright PDF 文档](https://playwright.dev/docs/api/class-page#page-pdf)：Playwright 支持通过浏览器环境生成 PDF，适合服务端报告导出。
- [web.dev PWA 文档](https://web.dev/learn/pwa/)：PWA 可让 Web 应用具备接近应用的安装和访问体验。
