# 技术栈

## 1. 结论

你的新要求是“随时随地随取随用”，这会改变技术选型结论：

**我建议首版做成云端 Web 应用 + PWA，而不是 Windows 本地桌面应用。**

用户只要打开网址就能使用，电脑、平板、手机都能访问；后续也可以把网页添加到桌面，接近 App 的使用体验。

推荐技术组合：

| 层级 | 推荐 | 选择理由 |
|------|------|----------|
| 产品形态 | 云端 Web 应用 + PWA | 满足随时随地访问，不需要安装软件，不绑定某一台电脑 |
| 前端框架 | Next.js + React + TypeScript | 一个项目同时覆盖页面、接口和服务端逻辑，适合快速交付业务工具 |
| UI 组件 | Ant Design | 表单、表格、导入、弹窗、提示、筛选都成熟，适合纸箱配纸这种业务工具 |
| 后端方式 | Next.js Server Actions / API Routes | 首版不用单独拆一个后端项目，降低开发和部署复杂度 |
| 数据库 | PostgreSQL | 云端多人/多设备访问时，比 SQLite 更适合长期保存纸厂、原纸、公式和历史方案 |
| 数据访问 | Drizzle ORM | 类型清晰、迁移简单，适合 TypeScript 项目和结构化业务表 |
| 文件存储 | 对象存储 OSS/COS/S3 | 保存导出的 PDF、Excel、JSON 备份文件，不放在应用服务器本地 |
| Excel/CSV 导入导出 | ExcelJS + PapaParse | ExcelJS 负责模板和导出，PapaParse 负责 CSV，稳定且贴合文档要求 |
| PDF 导出 | 服务端 HTML 模板 + Playwright/Chromium 生成 PDF | 云端环境不能用 Electron 打印，改用服务端浏览器渲染报告 |
| AI 选型理由 | AI Provider 接口 + 缓存 + 模板降级 | AI 只负责解释，不参与核心计算；失败时不影响方案生成 |
| 登录与安全 | 首版单账号/简单账号体系，后续扩展角色权限 | 文档首版不做复杂权限，但云端必须有登录保护数据 |
| 钉钉集成 | 钉钉作为入口、登录、通知和文件归档，不作为主数据库 | 钉钉适合协同入口，但不适合承载配纸计算所需的复杂查询、事务、版本追溯和性能要求 |
| 部署 | 国内用户优先：阿里云/腾讯云服务器 + PostgreSQL + 对象存储；海外/跨境可选 Vercel + Supabase | 纸箱厂用户大概率在国内，访问稳定性比“热门”更重要 |
| 测试 | Vitest + Playwright | 公式、搜索、导入导出、方案调整都要可验证 |

一句话结论：我建议选 **Next.js + TypeScript + PostgreSQL + 对象存储 + PWA**。它比桌面应用更适合“随时随地随取随用”，又不会像大型企业系统那样过度复杂。

## 2. 产品约束判断

| 约束 | 判断 | 对技术选型的影响 |
|------|------|------------------|
| 使用方式 | 用户明确要求随时随地随取随用 | 必须优先 Web/PWA，而不是本地桌面安装包 |
| 目标用户 | 工艺人员、销售业务员 | 需要电脑端高效录入，也要手机端能查看和简单操作 |
| 首版范围 | 单次配纸、数据维护、方案调整、历史保存、导出 | 不需要复杂微服务，单体 Web 应用更合适 |
| 用户量级 | 文档首版不做多用户和权限 | 仍然需要最小登录保护；复杂角色权限后置 |
| 数据资产 | 纸厂、原纸、公式、历史方案是核心资产 | 数据应放云端数据库，并提供导出备份 |
| 数据规模 | 数百条原纸数据 + 最近 50 条历史方案起步 | PostgreSQL 足够，不需要搜索引擎或分布式数据库 |
| 性能要求 | 单次方案生成 ≤ 5 秒 | 计算逻辑放服务端执行，按文档分层过滤，避免前端设备性能差异 |
| 文件要求 | Excel/CSV 导入，PDF/Excel/JSON 导出 | 需要服务端文件处理和对象存储 |
| AI 要求 | 生成选型理由，失败时模板降级 | AI 封装为独立服务，缓存、限额、超时都要做 |
| 数据安全 | 云端访问比本地更方便，也更需要安全 | HTTPS、登录、数据库备份、操作日志要作为基础能力 |

## 3. 推荐架构

整体采用云端单体架构：

| 模块 | 技术 | 职责 |
|------|------|------|
| 页面层 | Next.js App Router + React + Ant Design | 参数录入、方案对比、数据维护、设置、历史方案 |
| 服务端层 | Next.js Server Actions / API Routes | 处理配纸生成、导入导出、AI 调用、数据库读写 |
| 计算层 | TypeScript 纯函数模块 | 面积、强度、成本、设备限制、瓦型层数推荐、搜索策略 |
| 公式层 | JSON 公式配置 + 安全表达式解析 | 保存公式输入、输出、条件、中间变量和版本号 |
| 数据层 | PostgreSQL + Drizzle ORM | 保存纸厂、箱板纸、瓦纸、基础参数、公式版本、历史方案 |
| 文件层 | 对象存储 | 保存 PDF、Excel、JSON 备份和导入模板 |
| AI 层 | 可替换 AI Provider | 选型理由生成、缓存、每日上限、失败模板降级 |
| 安全层 | 登录、HTTPS、数据库备份、操作日志 | 保护原纸价格、公式和历史方案 |
| 测试层 | Vitest + Playwright | 公式单元测试、主流程端到端测试、导入导出测试 |

建议目录结构：

```text
src/
  app/                  # Next.js 页面和路由
  components/           # 通用表单、表格、弹窗、状态标签
  server/               # 服务端动作、接口、权限校验
  domain/               # 配纸计算、公式、搜索、校验
  db/                   # PostgreSQL schema、迁移、仓储
  import-export/        # Excel、CSV、JSON、PDF
  ai/                   # AI Provider、缓存、模板降级
  storage/              # 对象存储封装
  shared/               # 前后端共享类型
  tests/                # 单元测试和端到端测试
```

这个架构仍然保持首版简单：不是微服务，也不是重型企业系统；只是把原来“本地电脑里的数据”换成“云端数据库里的数据”。

## 4. 关键技术选择说明

### 4.1 产品形态：Web/PWA、桌面应用、小程序

| 方案 | 适合场景 | 不适合点 |
|------|----------|----------|
| Web/PWA | 随时随地打开网址使用，电脑、平板、手机都能访问 | 离线能力不如纯桌面应用 |
| 桌面应用 | 固定电脑使用、强本地文件能力、无需联网 | 不满足随时随地取用 |
| 小程序 | 手机轻量使用、微信内传播 | 复杂表格、Excel 导入、PDF 导出和后台数据维护不如 Web 顺手 |

我建议选 **Web/PWA**，因为你明确要随时随地使用。销售在客户现场、工艺人员在办公室、老板在手机上查看，都可以通过同一个网址进入。

### 4.2 前后端框架：Next.js、传统前后端分离、低代码

| 方案 | 适合场景 | 不适合点 |
|------|----------|----------|
| Next.js | 一个项目同时做页面、接口、服务端逻辑，适合小团队快速交付 | 后续超大团队协作时可能需要拆分服务 |
| React + 独立后端 | 前后端团队分工明确、后端接口复杂 | 首版会多一个项目和部署链路 |
| 低代码 | 内部简单表单和审批 | 配纸公式、搜索策略、PDF 报告、AI 理由都较难做扎实 |

我建议选 **Next.js**，因为它是全栈 React 框架，可以把页面、服务端逻辑和接口放在一个项目里，减少首版开发和部署复杂度。

### 4.3 数据库：PostgreSQL、SQLite、MySQL

| 方案 | 适合场景 | 不适合点 |
|------|----------|----------|
| PostgreSQL | 云端应用、结构化数据、后续权限和报表扩展 | 比本地 SQLite 多一点运维 |
| SQLite | 单机本地工具 | 不适合多设备云端访问 |
| MySQL | 常见业务系统 | 可以用，但 JSON、复杂约束和后续扩展上 PostgreSQL 更舒服 |

我建议选 **PostgreSQL**，因为“随时随地”意味着数据要放在云端，PostgreSQL 比 SQLite 更适合长期演进，也比上来做复杂分布式数据库更克制。

### 4.4 部署：国内云、Vercel + Supabase、自建服务器

| 方案 | 适合场景 | 不适合点 |
|------|----------|----------|
| 国内云服务器 + 云数据库 + 对象存储 | 主要用户在国内，追求访问稳定、数据可控 | 初始配置比 Vercel 稍麻烦 |
| Vercel + Supabase | 海外访问、快速上线、低运维 | 国内访问稳定性需要实际验证 |
| 单台自建服务器全包 | 成本低、结构简单 | 数据库和文件备份风险更高 |

我建议选 **国内云优先**。如果你的用户主要在国内纸箱厂，访问稳定性比“部署最省事”更重要。可以选阿里云或腾讯云：应用服务/云服务器 + PostgreSQL 云数据库 + OSS/COS 对象存储。

如果只是先做原型给少数人试用，也可以先用 **Vercel + Supabase** 快速跑起来；但正式给国内用户长期使用前，建议做访问速度和稳定性验证。

### 4.5 登录与权限：无登录、简单登录、完整权限系统

| 方案 | 适合场景 | 不适合点 |
|------|----------|----------|
| 无登录 | 只在本机使用或纯演示 | 云端会暴露原纸价格、公式和历史方案，不安全 |
| 简单登录 | 首版单公司、少量账号 | 暂时不支持复杂角色控制 |
| 完整权限系统 | 多部门、多门店、多角色协作 | 文档首版不包含，过早开发会拖慢进度 |

我建议首版选 **简单登录**。文档说首版不做多用户和权限管理，但云端系统不能裸奔；至少要有账号密码登录，后续再加工艺、销售、管理员等角色。

### 4.6 PDF 导出：服务端生成、浏览器打印、第三方服务

| 方案 | 适合场景 | 不适合点 |
|------|----------|----------|
| 服务端 HTML + Playwright 生成 PDF | 报告排版可控，和网页预览一致 | 需要部署 Chromium 运行环境 |
| 浏览器打印 | 实现最快 | 不同设备导出效果可能不一致 |
| 第三方 PDF 服务 | 报告量大、模板复杂 | 多一个外部依赖和成本 |

我建议选 **服务端 HTML + Playwright/Chromium 生成 PDF**，因为配纸报告需要稳定、正式、可发给客户，不能依赖每台手机或电脑自己的打印效果。

### 4.7 AI 选型理由：直接调用、封装服务、模板生成

| 方案 | 适合场景 | 不适合点 |
|------|----------|----------|
| 前端直接调用 AI | 快速演示 | API Key 暴露风险高，无法统一限额 |
| 服务端 AI Provider | 可替换供应商、可缓存、可限额、可降级 | 要多写一层服务 |
| 纯模板生成 | 不依赖 AI | 解释质量有限，不符合文档中 AI 理由要求 |

我建议选 **服务端 AI Provider**，因为文档明确要求 AI 失败时不能阻断方案生成。服务端统一控制超时、缓存、每日上限和模板降级，是最稳的做法。

### 4.8 钉钉定位：入口、协同和归档，不做主数据库

| 用法 | 是否建议 | 说明 |
|------|----------|------|
| 钉钉工作台入口 | 建议 | 用户从钉钉打开配纸工具，符合“随时随地随取随用” |
| 钉钉登录 | 建议 | 可用钉钉组织身份减少单独账号管理成本 |
| 钉钉消息通知 | 建议 | 方案生成完成、导出完成、异常提醒可发到钉钉 |
| 钉钉文件/群文件归档 | 可选 | 可把最终 PDF 报告或备份文件同步到钉钉，方便分享 |
| 钉钉表格/宜搭表单作为业务台账 | 可选 | 可作为人工查看和轻量维护入口，但不承载核心计算 |
| 钉钉作为主数据库 | 不建议 | 配纸工具需要复杂条件筛选、批量组合计算、公式版本、历史快照、事务一致性和性能保障，钉钉不适合作为底层主库 |

我建议的做法是：**PostgreSQL 做主数据库，钉钉做入口和协同层**。也就是数据真正保存在自己的云端数据库里，钉钉负责打开工具、识别用户、发送通知、分享报告。这样既能利用钉钉的便利，又不会把核心业务绑死在协同平台的数据能力上。

可以同步到钉钉的数据：

| 数据 | 同步方式 |
|------|----------|
| 最终配纸报告 PDF | 生成后上传/分享给指定钉钉会话或文件空间 |
| 精简方案表 | 作为 PDF 或 Excel 附件同步 |
| 方案摘要 | 以消息卡片形式发送：客户/尺寸/推荐方案/成本/是否达标 |
| 原纸数据备份 | 周期性导出 Excel 后归档 |

不建议只放在钉钉里的数据：

| 数据 | 原因 |
|------|------|
| 原纸主数据 | 需要强校验、索引、版本和批量查询 |
| 公式配置 | 需要版本控制、回滚、严格变量绑定 |
| 方案历史 | 需要价格快照、参数版本、调整记录和导出记录 |
| AI 缓存 | 需要按输入和方案组合精确命中 |
| 计算中间结果 | 属于系统内部数据，不适合暴露在协同表格里 |

## 5. 首版落地方案

首版建议先做这些：

| 范围 | 落地内容 |
|------|----------|
| 云端访问 | 绑定域名、HTTPS、账号登录、电脑和手机都能打开 |
| PWA | 支持添加到桌面/手机主屏，像 App 一样进入 |
| 数据维护 | 纸厂、箱板纸、瓦纸、基础参数、公式配置 |
| 导入 | Excel/CSV 导入，失败行提示具体原因 |
| 配纸计算 | 面积、耐破、边压、空箱抗压、成本、设备限制 |
| 推荐策略 | 经济型、安全型、均衡型三套方案，按文档分层过滤搜索 |
| 方案调整 | 可调整瓦型、层数、纸厂、克重，自动重新校核 |
| 历史方案 | 保存最近 50 条，包含输入、价格快照、参数版本、结果、导出记录 |
| 导出 | 完整配纸报告 PDF、精简方案表 PDF、原纸 Excel、公式 JSON、历史 Excel |
| AI 理由 | AI 生成 + 缓存 + 每日上限 + 超时模板降级 |
| 备份 | 数据库自动备份，原纸/公式/历史支持手动导出 |

首版建议暂缓这些：

| 暂缓项 | 原因 |
|--------|------|
| 复杂角色权限 | 文档首版不包含，先做简单登录 |
| 多租户 | 如果只是一个公司使用，不需要一开始做 SaaS |
| 小程序 | 配纸主流程更适合 Web 表格和报告页面 |
| 桌面客户端 | 与随时随地使用目标冲突，可以后续作为离线增强 |
| 供应商价格自动同步 | 文档明确后续迭代，首版用 Excel/CSV 导入更稳 |
| 批量配纸 | 当前产品定位是单次配纸决策 |

## 6. 后续扩展路径

| 触发条件 | 扩展方式 |
|----------|----------|
| 公司内多人同时使用 | 增加用户角色：管理员、工艺、销售 |
| 多家公司使用 | 增加租户隔离，升级为 SaaS |
| 手机使用频率很高 | 优化移动端方案查看、报价分享、扫码进入 |
| 现场网络不稳定 | 增加离线草稿和稍后同步，或补一个桌面离线版 |
| 导出报告模板变多 | 增加报告模板管理 |
| 价格需要自动更新 | 增加供应商价格导入接口或定时同步 |
| 数据规模明显增大 | 增加索引、预计算候选组合、缓存高频纸厂/瓦型组合 |
| AI 解释要求更强 | 增加术语库、Prompt 版本、人工审核和重生成 |

这条路径的好处是：现在先满足“随时随地能用”，以后需要多人协作、权限、离线或 SaaS 时都有升级路线。

## 7. 风险与注意事项

| 风险 | 说明 | 建议处理 |
|------|------|----------|
| 云端安全 | 原纸价格、公式、历史方案都属于核心资产 | 必须启用登录、HTTPS、数据库备份和导出备份 |
| 国内访问稳定性 | Vercel/Supabase 这类海外服务在国内访问体验不一定稳定 | 正式版本建议优先国内云，海外方案只适合快速原型 |
| 文档首版不含多用户 | 但云端必须至少有登录 | 首版做简单账号，不做复杂权限 |
| 公式口径存在差异 | PRD 提到内置默认公式，需求规格提到管理员后台导入公式 | 首版采用“默认公式 JSON 初始化 + 导入导出 + 版本号” |
| 垫板费用口径待确认 | 文档把垫板费用放入成本公式，但待确认事项提到是否首版必须参与 | 数据模型预留字段，默认可为 0，并在设置里明确展示 |
| PDF 中文排版 | 报告字段多，手机和电脑预览可能不同 | 以服务端 PDF 为准，从第一版就用真实长表格测试 |
| AI 供应商未确定 | 文档仅说明需要 AI 大模型接口信息 | 先做可替换接口；没有接口时使用模板理由 |
| 搜索性能 | 原纸组合可能达到数十万种 | 严格按文档分层过滤，每组最多计算前 200 种候选 |

## 8. 参考依据

- Next.js 官方文档说明它是用于构建全栈 Web 应用的 React 框架，适合把界面和服务端能力放在同一项目中。
- Supabase 官方文档列出 Postgres 数据库、认证、文件存储和实时能力，适合作为快速原型或海外部署的云后端选项。
- Vercel 官方文档说明 Next.js 可零配置部署，并提供全球性能和可用性增强；但国内正式使用前仍建议验证访问稳定性。
