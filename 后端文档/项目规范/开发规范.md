# 开发规范

本文档定义纸箱自动配纸工具项目的代码风格、命名约定、Git 工作流、测试策略、安全红线和 AI 协作协议。所有开发者和 AI 辅助开发都必须遵守本文档。

---

## 1. 语言与运行时要求

| 维度 | 规格 |
|------|------|
| 语言 | TypeScript 5.x，全栈统一使用 TypeScript |
| 运行时 | Node.js 20 LTS 及以上 |
| 框架 | Next.js App Router |
| 包管理器 | pnpm 9 及以上，禁止使用 npm / yarn 安装依赖 |
| 类型严格模式 | `strict: true`，禁止默认使用 `any` |
| 模块系统 | ESM，禁止新增 CommonJS 写法 |

`tsconfig.json` 必须启用以下关键配置：

```jsonc
{
  "compilerOptions": {
    "strict": true,
    "noImplicitAny": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "moduleResolution": "bundler",
    "target": "ES2022",
    "lib": ["DOM", "DOM.Iterable", "ES2022"]
  }
}
```

## 2. 代码风格与 Lint 规则

### 2.1 工具链

| 工具 | 职责 | 配置文件 |
|------|------|----------|
| Prettier | 代码格式化 | `.prettierrc.json` |
| ESLint | 代码质量检查 | `eslint.config.mjs` |
| TypeScript | 类型检查 | `tsconfig.json` |
| Vitest | 单元测试 | `vitest.config.ts` |
| Playwright | 端到端测试 | `playwright.config.ts` |

### 2.2 ESLint 规则概要

`eslint.config.mjs` 必须包含以下规则口径：

```js
import next from "@next/eslint-plugin-next";
import tseslint from "typescript-eslint";

export default tseslint.config({
  files: ["**/*.{ts,tsx}"],
  plugins: {
    "@next/next": next
  },
  rules: {
    "@typescript-eslint/no-explicit-any": "error",
    "@typescript-eslint/consistent-type-imports": ["error", { "prefer": "type-imports" }],
    "@typescript-eslint/no-unused-vars": ["error", { "argsIgnorePattern": "^_" }],
    "no-console": ["warn", { "allow": ["warn", "error"] }],
    "prefer-const": "error",
    "eqeqeq": ["error", "always"],
    "@next/next/no-html-link-for-pages": "error"
  }
});
```

### 2.3 格式化配置

`.prettierrc.json` 必须使用：

```json
{
  "semi": true,
  "singleQuote": false,
  "trailingComma": "all",
  "printWidth": 100,
  "tabWidth": 2,
  "useTabs": false,
  "endOfLine": "lf"
}
```

关键决策：

- 必须使用双引号：与 Next.js 和常见 TypeScript 项目默认风格一致。
- 必须保留分号：减少自动分号插入导致的边界问题。
- 行宽必须为 100：表格、类型和业务字段较多，80 会造成过度换行。

### 2.4 IDE 配置

`.vscode/settings.json` 必须包含：

```jsonc
{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit"
  },
  "typescript.tsdk": "node_modules/typescript/lib"
}
```

## 4. TypeScript 特定规范

### 4.1 类型导入

类型必须使用 `import type`。

```ts
// 正确
import type { PaperMaterial } from "@/modules/master-data/types";

// 错误
import { PaperMaterial } from "@/modules/master-data/types";
```

### 4.2 `interface` 与 `type`

| 场景 | 必须使用 | 原因 |
|------|----------|------|
| 业务实体对象 | `interface` | 便于表达可扩展结构 |
| 联合类型 | `type` | `interface` 无法表达联合 |
| 函数返回结果 | `type` | 便于组合成功/失败结果 |
| React 组件 Props | `interface` | 可读性更高 |

```ts
// 正确
interface PaperMaterial {
  code: string;
  gramWeight: number;
}

type SchemeStatus = "qualified" | "unqualified" | "not-manufacturable";

// 错误
type PaperMaterial = {
  code: string;
  gramWeight: number;
};
```

### 4.3 禁止的写法

#### 禁止默认使用 `any`

```ts
// 错误
function parsePaper(row: any) {
  return row.code;
}

// 正确
interface ImportedPaperRow {
  code: string;
  gramWeight: number;
}

function parsePaper(row: ImportedPaperRow) {
  return row.code;
}
```

#### 禁止无理由使用非空断言

```ts
// 错误
const code = row.paperCode!;

// 正确
if (!row.paperCode) {
  return { ok: false, error: "原纸代码为空" };
}
const code = row.paperCode;
```

#### 禁止用浮点数直接比较金额或成本

```ts
// 错误
if (costA === costB) {
  return "same";
}

// 正确
const COST_EPSILON = 0.0001;
if (Math.abs(costA - costB) < COST_EPSILON) {
  return "same";
}
```

#### 禁止把业务单位藏在变量名之外

```ts
// 错误
const width = 1710;

// 正确
const maxBoardWidthMm = 1710;
```

#### 禁止修改入参

```ts
// 错误
function normalizeInput(input: BoxInput) {
  input.lengthMm = Math.round(input.lengthMm);
  return input;
}

// 正确
function normalizeInput(input: BoxInput): BoxInput {
  return {
    ...input,
    lengthMm: Math.round(input.lengthMm)
  };
}
```

## 5. Next.js / React 特定规范

### 5.1 组件设计原则

- 页面组件必须只负责页面布局、数据读取和用户交互。
- 核心计算必须放在 `src/modules/calculations/`。
- 推荐策略必须放在 `src/modules/recommendation/`。
- 原纸代码映射必须放在 `src/modules/paper-code/`。
- 客户端组件必须只在需要浏览器交互时使用 `"use client"`。

### 5.2 组件文件结构

```tsx
"use client";

import type { MatchingScheme } from "@/modules/recommendation/types";

import { Button, Table } from "antd";

interface SchemeTableProps {
  schemes: MatchingScheme[];
  onExport: (schemeId: string) => void;
}

export function SchemeTable({ schemes, onExport }: SchemeTableProps) {
  return (
    <Table
      rowKey="id"
      dataSource={schemes}
      columns={[
        { title: "方案", dataIndex: "name" },
        { title: "含税成本", dataIndex: "taxIncludedCost" }
      ]}
    />
  );
}
```

### 5.3 导入导出规则

- 业务组件必须使用命名导出。
- 页面文件 `page.tsx`、布局文件 `layout.tsx` 必须使用默认导出，这是 Next.js 约定。
- 禁止在 `index.ts` 中做过深的桶导出，避免循环依赖。

```ts
// 正确
export function SchemeStatusTag() {}

// 错误
export default function SchemeStatusTag() {}
```

### 5.4 导入排序

导入必须按以下顺序分组，组间空一行：

```ts
// 1. React / Next.js
import Link from "next/link";

// 2. 第三方库
import { Button } from "antd";

// 3. 项目绝对路径
import type { PaperMaterial } from "@/modules/master-data/types";
import { calculateCost } from "@/modules/calculations/calculate-cost";

// 4. 相对路径
import { LocalToolbar } from "./local-toolbar";
```

### 5.5 Hooks 使用规范

- 自定义 Hook 必须以 `use` 开头。
- 只被某页面使用的 Hook 放在该页面 `_hooks/` 中。
- 多页面复用 Hook 放在对应业务模块或 `src/shared/`。
- Hook 中禁止直接写核心业务公式。

```ts
// 正确
function useMatchingForm() {}

// 错误
function matchingFormHook() {}
```

## 6. 样式规范

### 6.1 唯一样式方案

本项目必须使用 **Ant Design + CSS Modules / 全局主题变量**。

- 复杂业务控件优先使用 Ant Design。
- 页面局部样式使用 CSS Modules。
- 全局颜色、间距、字体变量放在 `src/styles/`。
- 禁止引入 Tailwind、styled-components 或其他样式体系，除非技术方案正式变更。

```tsx
// 正确
import styles from "./scheme-table.module.css";

export function SchemeTableHeader() {
  return <div className={styles.header}>方案对比</div>;
}
```

### 6.2 禁止的样式写法

```tsx
// 错误：业务组件中堆内联样式
<div style={{ marginTop: 12, color: "red" }}>未达标</div>

// 正确：使用组件属性或 CSS Module
<div className={styles.unqualified}>未达标</div>
```

```tsx
// 错误：用颜色表达唯一状态
<span className={styles.redText}>不可生产</span>

// 正确：颜色 + 文案共同表达
<Tag color="error">不可生产（超过设备最大宽度限制）</Tag>
```

## 7. Git 工作流

### 7.1 分支策略

当前项目按小团队/AI 协作模式执行简化 GitHub Flow。

```text
master
  ↑
feat/paper-code-mapping
fix/cost-unit-conversion
docs/update-prd
```

| 规则 | 说明 |
|------|------|
| 主分支 | `master`，必须保持可运行 |
| 功能分支 | 从 `master` 创建，完成后合并回 `master` |
| 分支生命周期 | 单个分支必须聚焦一个任务 |
| 合并方式 | 默认 Squash Merge 或普通 merge，禁止无意义 merge commit |

### 7.2 分支命名规范

```text
<type>/<short-description>
```

| 类型 | 用途 | 示例 |
|------|------|------|
| `feat/` | 新功能 | `feat/historical-order-scoring` |
| `fix/` | Bug 修复 | `fix/paper-code-case-sensitive` |
| `refactor/` | 重构 | `refactor/calculation-modules` |
| `docs/` | 文档更新 | `docs/dev-standards` |
| `test/` | 测试补充 | `test/area-formulas` |
| `chore/` | 构建/配置 | `chore/eslint-config` |

### 7.3 提交信息规范

提交信息必须遵循 Conventional Commits：

```text
<type>(<scope>): <subject>

[body]

[footer]
```

#### 类型

| 类型 | 说明 |
|------|------|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `refactor` | 不改变行为的重构 |
| `style` | 格式调整 |
| `docs` | 文档变更 |
| `test` | 测试相关 |
| `chore` | 构建、工具、依赖 |
| `perf` | 性能优化 |
| `ci` | CI/CD 配置 |

#### 作用域

| scope | 对应范围 |
|-------|----------|
| `auth` | 登录、会话、访问保护 |
| `master-data` | 纸厂、原纸、基础参数 |
| `paper-code` | 原纸代码映射 |
| `box-spec` | 纸箱输入与校验 |
| `formulas` | 公式和参数版本 |
| `calculations` | 面积、强度、成本、设备限制 |
| `recommendation` | 推荐策略 |
| `historical-orders` | 历史订单习惯分析 |
| `import-export` | 导入导出 |
| `ai` | AI 选型理由 |
| `docs` | 文档 |
| `infra` | 配置、部署、依赖 |

#### subject 规则

- 必须使用中文或简洁英文，保持同一次提交内一致。
- 必须使用祈使句或结果描述。
- 禁止句号结尾。
- 长度不超过 72 个字符。

#### 示例

```text
feat(paper-code): 增加原纸代码大小写敏感校验

历史订单中 dc 可能对应 dC 或 DC，不能自动修正。
本次新增疑似候选输出，要求用户人工确认。
```

```text
fix(calculations): 修正边压展示单位换算

计算内部使用 N/m，界面展示为 kN/m。
此前直接展示内部值会导致结果放大 1000 倍。
```

```text
docs(structure): 补充历史订单模块边界
```

## 8. 代码注释规范

### 8.1 何时写注释

| 需要注释 | 不需要注释 |
|----------|------------|
| 公司公式口径与常规公式不同 | 变量名已经清楚表达含义 |
| 为兼容历史数据脏值做特殊处理 | 简单赋值 |
| AI 降级、缓存、限额的业务原因 | 函数名已经说明动作 |
| 设备限制与机器方向绑定 | 重复描述代码做了什么 |

### 8.2 注释风格

```ts
// 正确：解释为什么不能忽略大小写
// 原纸代码中 dC 与 DC 分别代表不同原纸，历史订单导入必须精确匹配。
const matchedPaper = paperCodeMap.get(inputCode);

// 错误：复述代码
// 获取原纸
const matchedPaper = paperCodeMap.get(inputCode);
```

### 8.3 TODO / FIXME / HACK 标记

```ts
// TODO(owner, 2026-07-15): 补充三层和五层两片成箱公式，当前 PRD 明确暂不支持。
// FIXME(owner, 2026-07-15): 修复导入时把 250g 当作原纸代码的问题。
// HACK(owner, 2026-07-15): 临时兼容旧订单中的小写楞别 b，后续导入清洗时统一处理。
```

## 9. 错误处理规范

### 9.1 服务端错误处理

服务端动作必须返回统一结果类型：

```ts
type ActionResult<T> =
  | { ok: true; data: T }
  | {
      ok: false;
      error: {
        code: string;
        message: string;
        details?: Record<string, unknown>;
      };
    };
```

错误码必须使用稳定英文码：

| 错误码 | 场景 |
|--------|------|
| `VALIDATION_ERROR` | 输入校验失败 |
| `DATA_NOT_FOUND` | 数据不存在 |
| `PAPER_CODE_UNMATCHED` | 原纸代码无法匹配 |
| `FORMULA_PARAMETER_MISSING` | 公式或参数缺失 |
| `NOT_MANUFACTURABLE` | 设备限制不满足 |
| `AI_UNAVAILABLE` | AI 不可用，已降级 |
| `EXPORT_FAILED` | 导出失败 |

### 9.2 客户端错误处理

- 用户提示必须使用业务语言，不展示堆栈。
- 表单错误必须定位到具体字段。
- 导入错误必须能导出失败行和失败原因。
- AI 失败不得阻止方案生成，必须显示模板理由。

```ts
// 错误
message.error(error.stack);

// 正确
message.error("原纸代码 dc 无法唯一匹配，请人工确认。");
```

### 9.3 安全原则

- UI 中禁止暴露数据库错误、密钥、SQL 语句和原始堆栈。
- 客户端校验只用于即时反馈，服务端必须再次校验。
- 文件导入必须限制格式和大小。

## 11. 依赖管理

### 11.1 安装规范

```bash
# 正确
pnpm add zod
pnpm add -D vitest

# 禁止
npm install zod
yarn add zod
```

### 11.2 依赖审查

新增依赖必须满足：

- 解决明确问题，不能只为少量代码引入大包。
- 必须支持 TypeScript。
- 必须适配 Next.js 服务端或客户端运行环境。
- Excel、PDF、数据库、AI 相关依赖必须先查现有技术栈文档。

禁止：

- 为格式化日期引入大型工具库。
- 为简单计算引入数学表达式大框架。
- 未经确认引入另一套 UI 组件库。

### 11.3 版本锁定

- `pnpm-lock.yaml` 必须提交。
- 禁止手改锁文件。
- 升级依赖必须单独提交，提交类型使用 `chore(deps)`。

## 13. AI 协作协议

### 13.1 AI 写代码前必读

### 13.2 AI 写代码规则

| 规则 | 说明 |
|------|------|
| 读后写 | 修改文件前必须先读取该文件 |
| 最小改动 | 只修改任务要求范围，不做顺手重构 |
| 不猜版本 | 依赖版本交给包管理器和锁文件 |
| 不引入新依赖 | 除非任务明确需要，并说明原因 |
| 不写无意义注释 | 注释必须解释原因或业务口径 |
| 不创建多余顶层目录 | 顶层目录必须符合 `specs/项目结构.md` |
| 遵循模块边界 | 核心计算不得写进页面或 shared |
| 保护用户变更 | 不得回滚用户未要求回滚的改动 |
| 真实数据谨慎处理 | 真实订单和原纸数据不得复制到测试夹具，必须脱敏 |
| 提交信息规范 | 必须遵循 Conventional Commits |

### 13.3 AI 写完代码后必做

| 步骤 | 操作 |
|------|------|
| 1. 类型检查 | 运行 TypeScript 类型检查 |
| 2. Lint 检查 | 运行 ESLint |
| 3. 单元测试 | 涉及公式、映射、推荐时必须运行对应测试 |
| 4. 依赖方向 | 确认页面没有承载核心业务公式 |
| 5. 环境变量 | 如有新增，同步 `.env.example` |
| 6. 数据安全 | 确认未提交真实密钥和未脱敏样例 |

## 14. 目录依赖方向速查

合法依赖方向：

```text
src/app
  ↓
src/server/actions
  ↓
src/modules
  ↓
src/db / src/storage / src/shared

tests
  ↓
src/modules / src/server / src/app
```

禁止方向：

```text
src/modules ✗→ src/app
src/db ✗→ src/app
src/shared ✗→ src/modules
src/modules/calculations ✗→ src/modules/ai-reasoning
src/modules/calculations ✗→ src/server
src/modules/paper-code ✗→ src/modules/historical-orders
```

关键原则：

- `calculations` 必须是纯业务计算，不依赖页面、AI、数据库。
- `paper-code` 是历史订单分析的前置能力，不能反向依赖 `historical-orders`。
- `shared` 只能放通用能力，不能知道业务模块。

## 15. 安全编码规范

| 类别 | 规则 |
|------|------|
| 输入校验 | 所有用户输入必须在服务端校验，纸箱尺寸、重量、堆码、生产数量必须符合 PRD 范围 |
| 注入防护 | 数据库访问必须通过 Drizzle 查询构造，禁止拼接 SQL 字符串 |
| XSS | 用户输入展示时必须保持 React 默认转义，禁止随意使用 `dangerouslySetInnerHTML` |
| 密钥管理 | AI Key、数据库密码、对象存储密钥只能存在服务端环境变量 |
| 文件上传 | 只允许 `.xlsx`、`.xls`、`.csv`、`.json` 等明确格式，必须限制大小 |
| Excel 导入 | 导入内容必须作为不可信输入处理，不能执行表格中的公式或宏 |
| 认证检查 | 所有服务端动作必须检查登录状态 |
| 对象存储 | 导出文件必须有访问控制，禁止公开暴露敏感报告 |
| AI 输出 | AI 输出只能作为解释文案，不能反写核心计算结果 |
| 真实数据 | 真实订单数据、纸价、客户信息不得进入公开样例或测试快照 |
